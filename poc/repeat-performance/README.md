# リピートコマンドブロックの性能（#5）

同じスコア加算を、次の3経路で実行する。完成したコンバータやランタイムのベンチマークではなく、起動口と最小の書き込みキューの費用を測るPoC。

| 経路 | コマンドブロック | スクリプト側 |
| --- | --- | --- |
| native | `scoreboard players add b<ID> perf 1` | なし |
| custom | `je2be:perf <ID>` | 同期ハンドラでIDをキューへ積み、`runInterval` で同じBEコマンドを `runCommand` する |
| scriptevent | `scriptevent je2be:perf <ID>` | イベントハンドラでIDをキューへ積み、次の `runInterval` で同じBEコマンドを `runCommand` する |

100個を1チャンク（16列）、補助として500個を2チャンク（32列）と8チャンク（32列・2ブロック間隔）に配置する。すべて同じ `tickingarea` 内、y=-50、常時実行、遅延0。基準はコマンドブロックなし。同じ平坦ワールドで条件間のブロックとスコアを消し、20tickウォームアップ後に100tickを採取する。条件の順番を反転して2回ずつ測る。クライアント接続はない。

```sh
npm ci
npm run setup:servers
npm run build:pack
npx vitest run --config vitest.servers.config.ts poc/repeat-performance/performance.servers.test.ts
```

測定には専用worktreeのLinux BDSを使う（約2〜3分）。`results.json` に環境と集計、`samples.jsonl` に各条件の生データを保存する。全体の `npm run test:servers` でも実行する。スコア・キューの整合性は検証し、CPU時間やtick間隔の速さを固定閾値で判定しない。

## 指標

- **tick間隔（経過時間）**：`system.runInterval(..., 1)` の入口間の `Date.now()` 差。整数ミリ秒で、処理終了後の待機も含む。平均・中央値・p95・最大と75msを超えた回数を記録する。約50msでも処理に余裕があるかはわからない。
- **BDSプロセスのCPU時間/tick**：Linux [`/proc/<PID>/stat`](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html) の14・15番フィールド（user + system）を `getconf CLK_TCK` で秒へ換算し、測定前後の `ping` が返すtick差で割る。**全スレッドの合計であり、メインスレッドのMSPTではない。** スクリプト100tickの前後に入る起動・応答・ログ出力も窓に含まれるため、CPU窓のtick数と実時間も保存する。基準条件にも同じ測定器を入れる。
- **キュー反映時間**：毎tickのキューを `runCommand` で反映する区間の `Date.now()` 差。イベント配信やハンドラの費用は含まない。0msは整数ミリ秒の分解能未満という意味。
- **実際の更新数**：測定開始イベントと最後のサンプルで各IDのスコアを読み、差分を取る。100個では全IDが100回更新されたこと、スクリプト経路ではキューを処理した総数とスコア差分の合計が一致することを検証する。500個では実処理量も必ず併記し、異なる処理量のCPU値をそのまま比較しない。

`system.currentTick`、`runInterval`、カスタムコマンド、スコア取得・`runCommand` の仕様は固定した `node_modules/@minecraft/server/index.d.ts` に基づく。測定中はtickごとのログを出さず、終了後に10サンプルずつ出力する。

## 限界

スコア加算1命令だけを使う、ヘッドレスの小さな平坦ワールドである。パース・関数解釈・セレクタ検索・storage・永続化・実際のマップのチェーンは測っていない。デスクトップBDSの結果から、スマホや完成したランタイムの性能を保証しない。カスタムコマンドと `scriptevent` はキュー反映のtickが異なり、スコアの中間状態まで同じ意味論ではない。

CPU値は別プロセスのCPU使用を直接は含まないが、共有ホスト上の競合はtick間隔などに影響する。環境情報と開始時のload averageを併記する。500個で更新が間引かれる場合、処理の脱落やエンジンのスケジューリングとCPU飽和を切り分ける必要がある。

## 実測（2026-11-15）

BDS 1.26.63.1、Core i5-11400、WSL2/Linux x64。各行は順序を反転した2回の測定の範囲。根拠は同じディレクトリの `results.json` と `samples.jsonl`。

| 配置 | 経路 | 実更新数/tick | BDS全スレッド CPU ms/tick | tick間隔 p95 ms | キュー反映平均 ms |
| --- | --- | ---: | ---: | ---: | ---: |
| なし | 基準 | 0 | 1.54〜1.65 | 50〜51 | 0.00〜0.03 |
| 100個・1チャンク | native | 100 | 2.25〜2.33 | 51 | 0 |
| 100個・1チャンク | custom | 100 | 5.58〜5.92 | 52 | 1.39〜1.64 |
| 100個・1チャンク | scriptevent | 100 | 5.00〜5.69 | 51 | 1.86〜1.96 |
| 500個・2チャンク | native | 200 | 2.52〜3.01 | 51 | 0 |
| 500個・2チャンク | custom | 200 | 8.93〜9.41 | 53 | 2.42〜2.79 |
| 500個・2チャンク | scriptevent | 200 | 8.27〜8.35 | 51 | 2.93〜3.17 |
| 500個・8チャンク | native | 500 | 4.27〜4.41 | 52 | 0 |
| 500個・8チャンク | custom | 500 | 17.69〜18.45 | 52〜53 | 6.32〜6.41 |
| 500個・8チャンク | scriptevent | 500 | 16.15〜16.21 | 51〜52 | 6.12〜6.15 |

全条件でtick間隔の平均は49.97〜50.04ms、75ms超は0回。100個では全ブロックが100サンプル中100回ずつ更新され、起動と最小の書き込み処理は約20 TPSを保った。customのキューは起動と同tick、scripteventのキューは1tick後に反映された。

500個を2チャンクに密集させると全経路が200更新/tickだった一方、8チャンクに分散すると500更新/tickになった。間引かれた条件のCPU値を、500更新を処理した費用としては扱えない。密度に依存する更新制限の原因・閾値は追加調査の対象とする。
