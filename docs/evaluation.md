# ギミック単位の評価（#69）

静的集計（#47）が示すパース・BEコマンド出力の割合と、実際に動作を観測したギミックの割合を分ける。
記録は `evaluations/*.json` に置き、`npm run evaluate:gimmicks -- <記録.json>` で集計する。
型の定義と入力検証は `packages/converter/src/evaluation.ts`。

## 記録する内容

各ギミックには `id`、対応する `scenario`、開始条件 `start`、操作 `steps`、成功条件 `successCriteria`、
必須機能 `requiredFeatures`、進行上必須かを示す `required` を書く。成功条件は観測できる値で定義する。
機能の行数が少なくても、進行に必要なら必須として扱う。

`kind` は実測の `observed` と説明用の `illustrative` を区別する。説明用の値を実績へ合算しない。
`scope` はサーバー内の `server-scenario` と実クライアントの `client-playthrough` を区別する。
`staticReport` は静的集計への参照だけにし、行数をギミックの成立率の分母へ混ぜない。

| status | 意味 |
| --- | --- |
| unverified | 未検証、または成立を判断する証拠・比較が不足 |
| passed | 人手修正なしで成功条件を満たすことを観測 |
| passed-after-manual-fix | 記録した手修正を適用後、成功条件を満たすことを観測 |
| failed | 成功条件を満たさない箇所を観測。failuresに場所と理由を書く |

`evidence` にテスト名・コミット・実行日・ログ等の根拠を残す。既知差分は `knownDiffs`、
成功条件のうち比較できないものは `incomparable` に残す。テストが終了コード0でも、必須項目を
比較できなければ成立としない。証拠のない成立、必須比較が残った成立は集計時に未検証へ下げる。
既知差分のある成立は差分件数を表示し、完全一致とは呼ばない。成功条件に反する差分なら failed にする。

手修正は開発者が不成立の原因を調べるための記録であり、作者による生成物の修正を前提としない（#117）。
`fixes` に場所・理由・手順・再変換時の再適用要否を書き、`candidate` と `verified` を区別する。
手修正後の成立には全修正の検証根拠が必要。未実証の自動化や代替案は候補として記録し、適用済みとしない。

事前の変換レポートの警告は `warnings` にID・場所・文面を記録する。実際の不成立は `failures` に
場所・理由・対応する `priorWarningIds` と、事前に警告した `warned`／見逃した `missed`／未突合の `unverified` を残す。
`warned` は事前のレポートに存在する警告だけに使い、プレイ後に書いた説明を事前警告としない。
入力検証は警告IDの参照を確認するが、証拠の真偽や記録時刻を自動検証するものではない。

## 集計と完了判定

- 製品の指標である人手なしの成立率：passed / 全ギミック。手修正込みの成立率は原因調査用として別に出し、製品の指標に含めない。未検証は分母に残し、分子には含めない。
- 未検証・成立・手修正後成立・不成立の件数、既知差分・比較不能の件数を表示する。
- 警告捕捉率：warned / 実測した不成立箇所。未突合も分母に残す。分母0と説明用の記録は率を null にする。
- 必須ギミックの不成立・未検証を `blockers` として機能名付きで列挙する。
- `clearConfirmed` は実測したクライアントでの通しプレイの完了証拠があり、必須ギミックが存在し、
  全て成立している場合だけ true。1件でも必須ギミックが未検証・不成立なら false。

この集計は記録された成功条件と証拠の範囲を扱う。必須ギミック自体の登録漏れがないこと、
実クライアントでの取り込み・再読込・補助設定への非依存は #68、許可された実作品の最終確認は #48で確かめる。
サーバーのシナリオだけで製品・作品のクリア確認済みとはしない。

## 実例と説明用の例

`evaluations/scores-chain.observed.json` は自作の `scenarios/convert/scores-chain.json` に対応する。
スコアの再注入と、成功側／失敗側の条件付きチェーンの2ギミックを記録した。
JE 26.3 → Chunker 1.21.0 → BDS 1.26.63.1で同シナリオのJava・BEテストを3回連続成功
（2026-11-16、30.93 / 29.75 / 29.29秒）。観測スコアは正解データと一致し、既知差分・比較不能はなかった。
その2件の自動成立率は100%だが、ブリッジの補助を含むサーバー内検証なので clearConfirmed は false。
未検証の製品動作まで成功へ拡張しない。

`evaluations/gimmick-door.observed.json` は自作の `scenarios/datapack/gimmick-door.json`（#361）に対応する。
配布マップの関数の上位の型だけで作った扉の仕掛けを、初期化・委譲先のない行の後続・タイマーで開く・予約で閉じる・
繰り返しの予約の5ギミックに分けた。JE 26.3 → BDS 1.26.66.1 のランタイムで3回連続同じ結果（2026-11-28）。
繰り返しの予約は、同じ tick の `schedule` と `tick` 関数の順序が Java と逆なため不成立（#440）で、変換レポートは事前に警告していない。

`evaluations/required-gate.illustrative.json` は、必須の表示・クリックギミックが未検証で進行を保証できない
状況を示す説明用の例。実マップの不具合を観測した記録ではない。ボタンへの置換は未実証の手修正候補として
記録する。成立率はnull、必須ギミックはblockersに残り、clearConfirmedはfalseとなる。

エージェントは機能追加時に対応ギミックと成功条件を先に書き、実行したコミットと根拠を更新する。
修正前の失敗と事前警告の突合を残し、再変換時に手修正が失われる場合は再適用を記録する。
配布マップの非公開本文を記録へ持ち込まず、許可を得た観測範囲だけを公開する。
