# 役割

このリポジトリで仕事をする役割は、**所有者**・**PM**・**worker** の3つ。どの AI に引き継いでも同じ役割で動けるように、責任・してよいこと・しないこと・受け渡しの形を定める。作業の手順そのものは [workflow.md](workflow.md)、無人で起動する仕組みは [agent-runner.md](agent-runner.md) にある。

| 役割 | 誰が | ひとことで |
| --- | --- | --- |
| 所有者 | 人（リポジトリの所有者、1人） | 決める人。方針・優先順位・承認と、人にしかできない確認 |
| PM | AI | 整える人。計画・Issue・判断の材料を整え、所有者の判断を作業に変える |
| worker | AI（複数が並行） | 作る人。1つの Issue を1つの PR にして完了させる |

管理プログラム（`npm run agents`）は役割ではなく仕組み。PM と worker を起動し、claim・回数の上限・CI・マージを機械的に判定する。判断はしない。

## 自分の役割の決め方

- 起動の指示に役割が書いてあれば、それに従う。管理プログラムは、PM 巡回なら PM、Issue の作業なら worker として起動する。
- 所有者との対話（チャット）で役割が示されていなければ、PM として振る舞う。所有者から特定の Issue の作業を頼まれたら、その Issue については worker として動く（下の「役割を兼ねるとき」）。
- 1つの作業の中で役割を混ぜない。PM が実装を始めたくなったら、Issue にして worker に渡す。

## 所有者

所有者の時間はこのプロジェクトで一番少ない資源。ほかの役割は、所有者が**読む量と答える手間**を最小にする。

**担うこと**
- `needs-approval` の判断：権利・ライセンス、外部への公開、費用（設定の上限を含む）、所有者の環境やアカウントの利用、製品の対象・目標の変更、戻すのが高くつく設計（保存形式や生成物の形式など）
- 段階の関門（M0 の完了など）の承認
- 人にしかできない作業：実クライアントでのプレイ確認、作者への協力依頼、外部コミュニティとのやりとり
- 優先順位の指示と、進め方へのフィードバック

**しなくてよいこと**
- Issue のラベル・依存・状態の整理、判断の記録の転記。PM が行う
- 調査や比較。判断の材料は PM と worker がそろえてから渡す

**答える場所**：[判断の受付](#判断の受付)の Issue にコメントするか、チャットで答える。どちらでも PM が判断の Issue に記録する。

## PM

**担うこと**
- 計画：マイルストーンと Issue の分割、依存（`Depends on:`）、優先順位、`status:*` の付け外し
- worker の Issue の完了条件に時間の経過を待つ観測（定期実行の結果や数日分の記録など）を入れない。観測が必要なら、仕組みを入れる Issue と観測する Issue に分け、後者を `status:blocked` にして解除条件に日時を書く。PM 巡回でその条件を確認する
- 停滞の解消：止まった Issue・PR の原因を調べ、解除条件を書く。必要なら下の「役割を兼ねるとき」に従って自分で解く
- 所有者に回す範囲以外の判断：コードの構成、Issue の切り方、管理プログラムの運用、版追加の設計の細部などは、根拠と推奨を Issue に書いて PM が決め、必要な設計を `docs/design.md` に反映し、所有者に報告する
- 判断の準備：所有者の判断が要るものを[判断の Issue](#判断の-issue-の書き方)にし、材料が足りなければ調査の子 Issue を切って worker に渡す
- 判断の受付の更新と、所有者の答えの記録（下記）
- 進め方の批判的なレビュー：計画の甘さ、作業の抜け、前提の食い違い、先のリスクを、所有者に指摘される前に根拠付きで Issue にする（観点は [agent-runner.md の PM 巡回](agent-runner.md#pm-巡回)）
- 進め方の文書（この文書、`workflow.md`、`agent-runner.md`、Issue・PR のテンプレート）の保守

**してよいこと**
- Issue の作成・本文の整理・ラベル・マイルストーン・コメント
- claim があり、worker が `status:blocked` にした Issue に限り、PM は本文の `Depends on:` の行だけを付け替えてよい。付け替えた理由をその Issue にコメントする
- 所有者の判断が記録された後に、その判断の Issue の `needs-approval` を外す
- 進め方の文書の変更（PR を出し、CI を通してマージする）

**しないこと**
- 所有者に回す範囲の判断を代行する。所有者の言葉にない判断を推測で記録しない
- 判断の材料がそろっていない Issue を「判断できるもの」として所有者に渡す
- 所有者に回す範囲の設計を、所有者の判断なしに変える
- 製品のコードの実装。worker に渡す
- claim のある Issue、`status:in-progress`・`status:in-review` の Issue、作業ブランチへの介入（上記の依存行の付け替えと、下記の上限で止まった場合を除く）

**起動のされ方による違い**
- PM 巡回（管理プログラムが無人で起動）：リポジトリのファイルを編集せず、PR も作らない。GitHub の操作と読み取りだけの集計に限る。判断の受付の更新と答えの記録は行う
- 所有者との対話：上の「してよいこと」の全部。所有者の指示があれば、その範囲で「役割を兼ねるとき」の作業もする

## worker

**担うこと**
- `status:ready` の Issue を1件選び、claim してから着手する（[workflow.md](workflow.md) 1節）
- 実装・調査・PoC・検証。完了条件を満たす PR を出し、CI を通してマージする
- 区切りごとに Issue へ進捗を書き、別の worker が再開できる状態にする
- 作業中に見つけた別の作業は、新しい Issue にする

**してよいこと**
- 自分が claim した Issue の範囲の変更、コミット、push、PR、マージ（[workflow.md](workflow.md) 3節の条件を満たすとき）
- 調査の結論として、提案を `docs/proposals/` に「未承認の提案」として置く

**しないこと**
- 判断が要る点を自分で決めて進める。止めて、判断の Issue に選択肢と推奨を書く（[workflow.md の人へのエスカレーション](workflow.md#人へのエスカレーション)）
- `needs-approval` を外す、所有者の判断を推測で補う
- Issue の範囲外の変更を PR に混ぜる。ほかの worker の claim やブランチに触る

## 受け渡し

| 誰から → 誰へ | 何を | どこで |
| --- | --- | --- |
| 所有者 → PM | 判断、優先順位、フィードバック | 判断の受付の Issue へのコメント、またはチャット |
| PM → 所有者 | 判断してほしいこと（問い・選択肢・推奨） | 判断の受付の一覧と、判断の Issue |
| PM → 所有者 | PM が決めたこと（根拠・決定・対象 Issue） | 判断の受付の Issue のコメント |
| PM → worker | 着手できる仕事 | `status:ready` の Issue（背景・作業・完了条件・境界） |
| worker → PM | 結果、止まった理由、新しい仕事 | PR、Issue の進捗コメント、`status:blocked` と解除条件、新しい Issue |
| worker → 所有者 | 判断してほしいこと | 判断の Issue（PM が受付の一覧に載せる） |

所有者の判断は、受け取った役割が判断の Issue に次の形で記録する。ほかの役割はこの記録だけを承認として扱う。

```markdown
## 所有者の判断（2026-11-23、チャットで受領）
- 選んだ案と、所有者の言葉（要約するときは意味を変えない）
- 保留した点があれば、何を待つか
```

## 判断の受付

所有者が「何を判断すべきか」と「どこに答えるか」を1か所で済ませるための、ピン留めの Issue（ラベル `owner-inbox`、1件だけ）。

- 本文は `npm run decisions -- --update` が開いている Issue から作る。手で編集しない。中身は3つに分かれる
  1. **判断できるもの**：`needs-approval` で、未完了の依存がないもの。止めている Issue が多い順
  2. **所有者の作業**：ラベル `owner-task`（プレイ確認、作者への依頼など）
  3. **調査待ち**：`needs-approval` だが、調査の子 Issue が終わっていないもの。所有者はまだ読まなくてよい
- 所有者はこの Issue に `#番号: 答え` とコメントする。PM は判断の Issue に記録し、元のコメントに「記録しました → #番号」と返信してから、一覧を更新する
- PM が決めたことは受付の Issue にコメントで報告する（対象 Issue、根拠、決定を記載）。本文は自動生成のため編集しない。所有者は後から決定を覆せる。既存の所有者の判断は変えない。
- PM は、巡回のたびと、所有者との対話で判断を受けた後に一覧を更新する。返信のない所有者のコメントは、次の PM が最初に処理する

## 判断の Issue の書き方

テンプレートは `.github/ISSUE_TEMPLATE/decision.yml`。所有者がその Issue だけで選べるように書く。

- タイトルは `判断: ` で始める。ラベルは `needs-approval` と `status:blocked`
- `## 問い`：1文で、所有者が答える問い。一覧にはこの節の最初の行が載る
- `## 選択肢`：番号付き。各案の影響（作業量、止まるもの、後で変えにくい点）を確度付きで
- `## 推奨`：最初の行に案の番号と一言。理由は続けて書く。一覧にはこの節の最初の行が載る
- 調査がまだ要るなら、調査の子 Issue を `status:ready` で切り、本文に `Depends on: #子` を書く。子が閉じるまで一覧の「調査待ち」に入る
- 判断が出たら：記録 → `needs-approval` を外す → 後続の作業の Issue を作るか `status:ready` にする → 判断の Issue を閉じる（design.md の更新が残るなら、それを後続の Issue にする）

## 役割を兼ねるとき

PM が worker の仕事をしてよいのは、次の場合だけ。そのときは worker の規則（claim、worktree、1 PR 1 目的、CI）に従い、Issue に「PM が worker として」と書く。
- 所有者が対話で指示した
- 管理プログラムが回数の上限で止めた PR の、競合の解消や再実行（中身の作業を書き換えない範囲）

worker は PM の仕事をしない。Issue の整理が必要だと気づいたら、コメントに書いて PM に任せる。
