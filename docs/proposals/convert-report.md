機械向けの全コマンド文字列や UUID は詳細調査には有用だが、概要に全件表示すると作者が優先順位を付けにくい。合計と要対応を先に置き、詳細で元情報を展開する。入力由来の文字列・座標は作品情報なので、共有前に作者が内容を確認できるようにする。警告がないことを「動作保証」と表現しない。

## 台帳との対応案

台帳は `(family, id)` ごとの方式・実装状況・欠落・根拠であり、個々の変換箇所に対する警告一覧ではない。次は提案上の対応で、現行レポートに自動的な結合や網羅的検出があるという意味ではない。

| 台帳の項目・状態 | 作者向けの表示案 |
| --- | --- |
| `command`、`effect`、`entity`、`sound`、`particle` などの `native` / `rewrite` | 変換結果の詳細に対応キーと根拠の範囲を付ける。出力ありは動作確認済みと同義にしない |
| `approximation` または `loss` | 近似・欠落として、何が変わるかと確認箇所を示す。音のカテゴリ、粒子の引数など現行の issues を結び付ける |
| `impossible`、`loss-only`、書き換えの `unsupported` | 要対応として理由と場所を示す。click / hover のイベント喪失、配置エンティティの省略は対象ごとの根拠を区別する |
| `uninvestigated`、`unknown`、`planned`、キー不一致 | 未判定として表示し、未対応や安全と断定しない。版、検査対象外、キーがない場合も区別する |
| `partial` / `output` | 対応済みと一括表示せず、台帳の evidence の確度・版・範囲と個別警告を併記する |
| `component`、`advancement_trigger`、`loot_*`、`attribute`、`game_rule` 等 | 検出・位置づけが実装されるまで検査対象外と明示。台帳の存在だけで当該ワールドに警告があるとは言えない |

1箇所が複数キー・警告に対応し得る。位置と警告コード単位で表示し、台帳キーは複数参照できる形を提案する。ブロック・アイテム・リソースパックは台帳の対象外もある（#111、#119）。未検査、未判定、欠落、変換失敗、近似を別に数え、全件数の分母と検査範囲を示す。

## 作者が読む形

| 候補 | 利点 | 欠点 |
| --- | --- | --- |
| Markdown と既存 JSON | オフラインで開け、検索・差分・共有が容易。JSON は機械処理に残せる | 大量の箇所では長い。ビューアにより見え方が異なる |
| 単一 HTML と JSON | 絞り込み・折りたたみ・場所へのリンクを設けやすい | 生成・保守・入力文字列のエスケープが必要。環境によってスクリプトが使えない |
| ゲーム内の本 | ワールドを開いたまま確認できる | ページ数・文字量・検索に制約があり、変換失敗時やワールド外で確認しにくい |

**推奨：まず Markdown をワールド外のレポートとして JSON と併出**し、将来 HTML やゲーム内ビューを同じ構造化データから作る。概要に入力版・変換器版・検査範囲・未検査・要対応件数を置き、詳細は「何が／なぜ／次に何を確認・修正するか」、確度と根拠、元と出力を示す。対処が未確定ならその旨を示す。例えば `minecraft:overworld (12, 64, -3)` のコマンドブロック、または `data/<namespace>/function/<path>.mcfunction:行` のように Java 側の次元・座標、パック内相対パス・行を明示する（関数のパスは版により異なるため実際のパスを表示）。行番号は更新で変わるため識別子そのものにはしない。例は説明用で実測ではない。

## 手修正を保つ候補

| 候補 | 利点 | 更新時の問題 |
| --- | --- | --- |
| 出力ワールドを毎回手編集 | 道具が不要 | 再変換で失われ、手順の再現・差分確認が難しい |
| 出力への汎用パッチ | 任意の修正を記録できる | 生成物の構造や順序変更で誤適用しやすく、元との対応が不明瞭 |
| 元の場所に結び付けた宣言的上書き | 変更理由を元の箇所と一緒に管理でき、変換後に再適用可能 | 対象ごとの適用器と競合検出が必要。任意の手編集をすべて表せない |

**推奨：作者管理の別ファイルによる宣言的上書き**。まずコマンドブロックと関数の単位を対象候補とし、生成結果への直接編集は自動保存されないことを伝える。ファイルは元マップにも生成出力にも依存しない場所に置き、版付き形式、対象種別、Java 次元と座標またはパック識別子と実際の相対パス、対象内容のハッシュ、修正内容、理由を持つ。関数の行には行番号だけでなく元内容と前後文脈等の検証が必要。同一内容の重複は自動選択しない。これは設計候補であり、詳細形式・対応対象・適用順序は承認後に設計する。

各変換で元入力を照合し、新しい出力の生成後に上書きを適用する。対象が一意で元内容の期待値が一致したときだけ適用し、適用済み・不一致・対象消失・複数候補・形式や版の不適合をレポートする。不一致は黙って適用せず、作者が差分を見て修正を更新・破棄・明示的に再承認する。移動や改名は候補提示までとし自動追跡しない。複数の修正が同じ対象に衝突する場合も停止して解決を求める。元マップと既存出力は上書きせず、新しい出力への適用結果を確認可能にする。入力・出力のハッシュと変換器版を記録して、変換器の更新による生成結果の変化も再確認対象にする。

## #117 での判断

1. 作者向けは Markdown + JSON を基本とし、HTML とゲーム内の本は後続の表示手段とするか。
2. 場所と期待する元内容に結び付いた別ファイルを採用し、不一致時は自動適用しない方針とするか。
3. 初期対象をコマンドブロック・関数に絞り、他のエンティティやワールド編集は対応範囲外として明示するか。
