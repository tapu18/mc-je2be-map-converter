# ランタイムの実行モデル：提案と承認範囲

所有者は #93（2026-11-22）で方式 A、共有状態をランタイムに寄せる方針、起動直後のずれの許容、稼働中の tick のずれに関する原則を承認した。正本は `docs/design.md` 5.4〜5.6。後段が成否を使い同期評価できない委譲の扱いは未決（#93、#168）であり、以下の候補・推奨の全体が承認されたわけではない。以下は判断のための調査時点の記録。根拠は [#67 の PoC](../../poc/runtime-queue/README.md) と [結果](../../poc/runtime-queue/results.json)（Java 26.3、BDS 1.26.63.1、API 2.12.0-beta）。以下の候補の結果は、特記しない限り **推定** であり、候補自体を実装して実測した結果ではない。一致は #67 の限定された fixture に対する予測で、一般的な Java 互換性を意味しない。

## 一体として比較する候補

| | A：同期解釈と保留書き込み | B：依存単位を予約し後で実行 |
| --- | --- | --- |
| 起動と成否（#93 の1） | カスタムコマンドのハンドラで解釈し、許されない書き込みを保留。自前で確定できた成否を返す。確定できない成否を成功と仮定しない | ハンドラは起動を予約し、書き込み可能な段階で依存単位全体を実行。予約の成功は実行の成功ではない。BE の条件付きチェーン・比較器には後の成否を同期して返せないため、依存する部分もランタイムに移す必要がある |
| 委譲（2） | 後段が成否を使う場合は、Java と同じ成否を同期評価できる命令に限定。評価不能なら警告し、その経路をサポート対象外とする | 実行段階で委譲結果を取得でき、Java の成否と対応づけを検証した命令のみ許す。成否を使う後段はランタイム内で継続。対応不能なら警告・対象外 |
| 共有状態（3） | 読み書きの依存閉包を同じランタイム経路に寄せ、保留値を含む状態を読む。ネイティブとの競合が残る・判定できない場合は警告・対象外 | 同じ閉包をまとめて移し、実行中に順序どおり反映。外部ネイティブ処理との順序が保証できない場合は警告・対象外 |
| tick（4） | 保留反映、schedule、tick 関数の順を仮置き。起動前の準備完了を明示し、起動時差は警告する | 予約を順序付きで実行し、schedule と tick 関数の相対順を明示する。起動前の準備完了を明示し、起動時差は警告する |

閉包はスコアだけでなくブロック、エンティティ、storage、成否や比較器の依存も含む。動的セレクタ、外部パックやプレイヤー操作など静的に閉包を証明できない場合がある。警告は競合対象・場所・成否参照・起動順の影響と手修正候補を示す。閉包の検出が完全であるとは仮定しない。

## #67 の全ケースの予測

「条件付き」は表の前提が満たされる場合のみの推定。「対象外」は一致として数えない。A の現行 PoC における実測は右端に示す。

| ケース | A（推定） | B（推定） | #67 の実測（現行キュー） |
| --- | --- | --- | --- |
| 設置直後のブロック条件 | 条件付き：保留ブロックをオーバーレイで読む | 条件付き：同一単位内で設置後に読む | オーバーレイで一致 |
| 召喚直後のセレクタ | 条件付き：保留実体を選択に含める | 条件付き：召喚完了後に検索できる | 限定した種類・距離条件で一致 |
| 委譲した命令の成功 | 条件付き：成否を正しく同期評価 | 条件付き：結果の対応と後段の移行 | 一致 |
| 委譲した命令の実行時失敗 | 条件付き：失敗を同期評価、不能なら対象外 | 条件付き：結果を待ち後段も移行、外部比較器は対象外 | 不一致：成功を先に返す |
| 共有スコア | 条件付き：全依存を移しオーバーレイで順序を守る | 条件付き：全依存を移し同じ順序で実行 | 不一致：ネイティブの更新を上書き |
| コマンドブロック→tick 関数 | 条件付き：稼働時の順序を保証、起動差は対象外 | 条件付き：両方を移し順序を保証、起動差は対象外 | 稼働時は条件付き一致、起動時不一致 |
| tick 関数→コマンドブロック | 条件付き：稼働時の順序を保証、起動差は対象外 | 条件付き：両方を移し順序を保証、起動差は対象外 | 稼働時は条件付き一致、起動時不一致 |

#67 の召喚オーバーレイは並べ替え・上限・タグ・スコアや、実体化前の追加操作を検証していない。起動時の差は当該 fixture の観測であり、一般に常に1 tick ずれるという保証ではない。

## 推奨と所有者が選ぶ点

**推奨は A を制限付きで進めること**。既存の起動口と同期成否を保て、#67 が示したオーバーレイの有効範囲を使える。ただし、成否を推測して返す現行 PoC の振る舞い、混在状態の無条件許可、起動時一致の保証は採らない。対応不能な経路を黙って変換せず報告することが前提。成否評価の対応範囲や依存検出が十分かは後続実装で実測する必要があり、現時点で網羅性は未確認。

B を採らない理由は、予約時に実行結果を返せず、BE の条件付きチェーンや比較器と境界をまたぐ互換性を失うため。依存単位を広く移せば改善する可能性はあるが、その完全性と tick 順序は未検証。単に遅延するだけでは失敗時の成否を修復できない。

所有者は (1) A の制限付き対応か B の単位移行か、(2) 成否を検証できない委譲を対象外とする範囲、(3) 検出不能な共有依存を警告して手修正に委ねるか、(4) 起動時差を許容するかを選ぶ。反映→schedule→tick は仮置きであり、Java の順序との対応は未確認。起動差の解消策や B の実行可能性を保証するための新たな実験は、この提案の選択に必須の前提にせず、採用後の検証項目として残す。

#94 / #140 のスコア・storage の正本、永続化の選択は決めない。どちらの正本でも、同じ依存単位内の可視性と外部との同期境界を満たす必要がある。#95 / #141 のホスト境界とパック構成も決めないが、同期成否評価、保留値の読み取り、委譲結果と順序を表現できる契約が必要。2026-11-22 時点で #140・#141 に対応する PR は確認できず、両調査の結果が出たら整合性を再確認する。
