# 未承認の提案：スコアと storage の状態

#140 の調査を基に #94 で所有者が選ぶための提案であり、実装の決定ではない。以下の設計上の効果は推定であり、永続化や障害復旧の実測ではない。仮想 NBT は対象外。

## 1. スコアの正本

| 候補 | 利点 | 制約 |
| --- | --- | --- |
| BE スコアボード | ネイティブのチェーン・サイドバーと初期化パックが直接読む | ハンドラ内で書けない（`poc/launcher/`）；保留値を読む仕組みが必要。Java の演算や保持者の差を吸収する必要がある |
| ランタイムの型付き状態 | Java の整数演算・保持者・未反映値を統一して表現できる | BE への反映とネイティブからの更新取り込み、表示、競合解決が必要。共有時に古い値で上書きし得る（`poc/runtime-queue/`） |

**推奨**：ランタイムが担当する依存単位のスコアはランタイムを正本とし、BE スコアボードは表示・ネイティブ境界への投影とする。初期化パックの値を初回に取り込み、担当範囲を確定した後は双方向の無条件同期をしない。ネイティブも同じ値を変更する依存が残るか検出不能なら警告し対象外とする。名前・UUID の対応と削除も投影に含める。#93 の結論次第：同期モデル A ではハンドラ中の保留値を読み、後に投影する。予約モデル B では依存単位を後で順序通り実行して投影する。どちらも外部ネイティブとの順序や完全な依存検出は未検証。全スコアを BE 正本にする案は、ハンドラ書き込み制限と Java 演算の差を別途解決する必要がある。

## 3. storage の表現と保存

| 候補 | 利点 | 制約 |
| --- | --- | --- |
| `packages/core/src/nbt` の型付き表現を基にする | 数値の型、配列、リスト、複合を保持できる | Script API 境界のシリアライズとサイズ検証が必要 |
| 通常の JSON 値 | 扱いやすい | byte・short・int・long や配列の区別、long の精度を失う |

**推奨**：既存の型付き NBT を基にし、型タグと long の正確な表現を持つ版付き形式で保存する。文字列動的プロパティは UTF-8 32,767 バイト以下に分割し、名前空間・キー・世代・分割数を索引に持つ。32 MB まで上限に当たらなかったのは実測範囲であり、無制限の保証ではない（`poc/dynamic-properties/`）。変更した storage 単位だけ新世代を書き、保存頻度を tick 境界にまとめる案を推奨する。容量不足や書き込み失敗は明示し、黙って切り詰めない。形式、分割、負荷と再起動時の復元は未検証。

## 4. 保存の一貫性

| 候補 | 利点 | 制約 |
| --- | --- | --- |
| スコアと storage を別々に随時保存 | 実装が単純 | 中断時に異なる時点になる |
| 両方を同じ世代のスナップショットとして保存 | 復旧時に同じ確定世代を選べる設計 | BE の投影・ワールド保存との原子性は保証されない。容量と書き込み費用がある |

**推奨**：ランタイム正本のスコアと storage を同一世代で記録し、全片を書いた後に確定マーカーを更新、起動時は最後の完全な世代から復元し BE 投影を再構築する。旧世代は確定後に回収する。これは動的プロパティの書き込み順やクラッシュ時の永続性が原子的であるとの保証ではない。強制終了、部分書き込み、容量不足、BE ワールド側保存との前後関係を実測し、保証できない場合は復旧可能範囲を明示する。#93 の A/B いずれも確定境界を実行順と整合させる必要がある。

## 5. 初期値

| 候補 | 利点 | 制約 |
| --- | --- | --- |
| 変換時に初期化パックへ埋め込み | 既存のスコア初期化経路に近い | 大容量・分割とパックのサイズ、初回途中停止の扱いが必要 |
| ランタイム初回起動で変換済みデータを取り込み | 通常の型付き状態と世代管理を共用 | データの搬入と準備完了前の実行抑止が必要 |

**推奨**：変換器が Java の `command_storage_*.dat` を型付きで読み、版付き初期データをパックへ分割して埋める。ランタイムが初回に検証・世代を確定し、完了マーカー後に実行を許す。中断時は未確定世代を捨てて再試行し、既存の確定状態を初期値で上書きしない。スコア初期化との順序と UUID 対応を合わせ、#93 の起動時差も扱う。NBT の型・空値・大容量・失敗後再試行は後続実装で実測する。
