# ランタイムの構成

#141 の調査に対する #95 の所有者承認（2026-11-22）。実装は骨組みのみで、以下は目標の契約である。#93 の方式 A と #94 の状態設計に従う。

## 境界

解釈中核は Minecraft 非依存の `packages/core` に置く。既存のパーサと NBT の型を共有できる。別パッケージ案は公開境界と依存管理が増えるため採らない。Script API ホストは別パッケージ、生成パックの組み立ては converter が担う。`bridge-pack` は検証専用で製品は依存しない。ホストパッケージは `packages/runtime-host`（`@je2be/runtime-host`）。初期化処理を置き、Script API の利用をここに閉じ込める。

## ホスト契約

中核が Java の条件、セレクタのフィルタ・sort・limit、成否、分岐、予算を評価する。ホストは候補エンティティ、ブロックと状態の読み書き、ネイティブ委譲、保存、時刻を提供する。ホストにセレクタ全体を委ねる案は Java の意味が分散するため採らない。候補順、距離、乱数、失敗、未ロード領域を明示してフェイクで再現できるようにする。候補集合の Java と BE の一致は未確認。

#93 の方式 A として同期読み取り、保留書き込みのオーバーレイ、同期成否を要する。スコアは #94 のとおりランタイムが正本、BE は投影である。同期評価できない委譲の成否を成功と偽らない。成否に依存するチェーンを全体的に移すか静的処理の対象外にするかは #93 で未決定。共有状態はランタイムに寄せ、検出できない競合は警告する。起動直後のずれは許容し、稼働中の tick のずれは致命的とする。

### #234 の接続契約（#281）

これは #93 の方式 A、#94 のランタイム正本、#95 のホスト境界を実装するための限定的な接続判断であり、保存形式や #93 の未決定事項を変更しない。#234 はキューや起動口を作らない。以下の直接反映は書き込み可能な BDS の実行コンテキストでの接続検証に限り、カスタムコマンドのハンドラでの反映手段や tick 順序の解決とはしない（#19）。

- `executeCommand(state, ir)` は中核状態だけを操作し続ける。ホスト側の呼び出し口が実行前後のスコア状態を比較し、命令全体の実行終了後に追加・変更・削除された objective と保持者を BE に投影する。関数内や `execute store` の変更も含め、成功・失敗の結果だけから差分を推測しない。中核の結果と投影結果は別々に返す。中核の失敗でも既に生じた変更は投影対象とする。
- 投影は差分を決定的な順に適用し、最初の失敗で停止して対象と原因を返す。BE の部分反映はあり得るのでロールバックを約束しない。中核の変更は戻さず正本を維持し、投影を不整合とする。呼び出し元は以降の実行を止め、成功を報告しない。#234 は再試行キューや自動復旧を作らない。不整合の解消には安全なコンテキストで正本から再投影し、その成功を確認する必要がある。永続化・クラッシュ復旧は別途の保存設計に従う。
- API 操作は同期の成功値または分類された失敗を返し、例外も失敗に変換して原因を残す。ブロックの未ロード・範囲外、エンティティの不在・無効化、API 例外、非対応は区別する。不在と空の候補集合は同一ではなく、未ロードを空や air とみなさない。候補の取得が完全でない場合も不完全として返し、中核は完全な集合として評価しない。識別子はホスト内で解決し、取得後に無効となった対象への操作失敗を伝える。
- ネイティブ命令は API が同期で確定した結果を返せる場合だけその成否・値を返す。予約のみ、または実行成否が同期に得られない場合は `unknown` とし成功・失敗のどちらにも変換しない。#234 の検証用呼び出し口は `unknown` を診断して停止し、チェーンの振り分け方針は #93 に残す。
- #234 は候補取得、ブロックの読み書き、ネイティブ命令、スコア投影、動的プロパティの小さな型付き操作と分類された結果を定義・実装し、各操作の成功と関連する失敗を BDS で検証する。中核との接続は現行 `executeCommand` のスコア差分と投影に限る。セレクタの Java 意味論、オーバーレイ、キュー、状態の永続化プロトコル、load・tick 起動は実装しない。その他の操作は独立して試験できるが、中核が対応済みであることを意味しない。Script API の具体的な能力と制限は固定版の型と BDS 実測で確認し、実現できない契約は成功として扱わず #281 に根拠を戻す。

### ネイティブ委譲（#309）

ランタイムは `execute` の修飾句と関数フレームを評価し、ランタイム外の末尾命令を解決済みのコンテキストとともにホストへ渡す。BE ホストは実行者の `runCommand`（実行者なしならディメンションの `runCommand`）と `execute` の前置きで位置・向き・アンカー・ディメンションを渡す。

変換器はコマンドブロックと同じ書き換え処理でデータパックの末尾命令を判定し、書き換え結果を初期化パックの `data.js` の `nativeCommands` に渡す。版によって同じ行の結果が異なる場合は行の委譲を拒否する。書き換え結果がないときは `unsupported command` を返す。関数・タグの読み込みと load/tick 起動は #235 の範囲。

`RuntimeSession` は委譲直前と命令終了時に、最後に投影できた状態からのスコア差分を反映する。投影失敗時は委譲前に停止する。Script API が同期で成功件数を取得できる場合はその件数を返す。結果値が得られない場合は `unknown` を返し、実行中フレームの後続行や `execute store` への書き込みを行わない。

## 受け渡しとビルド

通常の関数は変換時に解析し版付き IR で渡す。IR 版と入力文法版を記録し、未知版と非対応命令を黙って実行しない。全本文をゲーム内でパースする案は反復解析と文法依存が増えるため採らない。IR の直列化形式は下記の版 1 とする。マクロも変換時に元版の文法で解析し、IR に型付きの穴を記録する（#316）。生成パックへの Java 文法の同梱は #107 の所有者判断に従う。

### CommandIR の直列化（スキーマ版 1）

`serializeCommandIR` は JSON オブジェクト `{ "schemaVersion": 1, "document": ... }` を返す。document は `grammarVersion`（入力文法の版を表す空でない文字列）、`textFormat`（`json` または `snbt`）、`ir`（`CommandIR`）を持つ。文法版を記録するだけで、版間の正規化や文法の互換性判定は行わない。マクロ行の IR は追加で `macro` を持つ。元版・テキスト形式と、穴のある引数の位置、型・読み取り条件、固定文字列と変数キーを保持する。

JSON の値は型を失わないよう再帰的に符号化する。文字列・真偽値・有限数・null はそのまま、配列は `["array", ...要素]`、通常オブジェクトは `["object", [キー, 値], ...]`、文字列キーの Map は `["map", [キー, 値], ...]` とする。整数型配列は `["int8", ...数値]`、`["int32", ...数値]`、`["int64", ...十進文字列]`、bigint は `["bigint", 十進文字列]`、負のゼロは `["number", "-0"]` とする。long は符号付き 64 ビットの範囲、配列の整数も各型の範囲に限る。オブジェクトと Map のキー重複、未知のタグ、構造不正、未知のスキーマ版は `deserializeCommandIR` が診断として拒否する。復号後の IR と引数の構造も検証し、非対応命令の実行可否は解釈器が別途判定する。

Java 26.3 の生成文法を使った Node テスト `ir-codec.servers.test.ts` では、シナリオ中の通常コマンド 415 件は合計 464,630 UTF-8 bytes（各コマンドを独立した文書として計測、マクロ行を除く）。これは圧縮前であり、パック全体の大きさではない。

[PoC](../poc/runtime-load/README.md) の BDS 1.26.63.1 で文法・対応表・パーサを含むパックは圧縮前 12,624,623 bytes、起動要求から初回パースまで 602 / 783 / 613 ms（ワールド準備を含む）、JSON.parse は 159 / 193 / 178 ms。再構成データ案は 12,210,907 bytes、手書き1命令・石1件の限定例は 50,929 bytes。後者は全機能版ではなく、実用版の大きさと性能は未確認。

`npm run build:pack` は runtime-host を型検査してから esbuild で `@je2be/core/runtime` と共に単一 ES モジュールに束ねる。中核の実行入口だけを参照し、文法・対応表は含めない。`@minecraft/server` と変換器が作る `data.js` は外部のままにし、変換器はバンドルとデータをパックに配置する。従来の `.js` 相対 import は tsc 出力を直接配布するためだったが、束ねる方式に合わせ `.ts` に統一した。`erasableSyntaxOnly` を維持する。ビルドは外部 import の許可リストと成果物の Node API 名を検査する。

実測（`packages/runtime-host/src/bundle.servers.test.ts`、BDS 1.26.63.1）：現在のバンドル `main.js` は 6,168 bytes（非圧縮、生成データ・manifest を除く）。空ワールドのテンプレート準備後、BDS 起動要求からテスト用ホストを介した中核の `scoreboard players set` の結果ログまで 1,085 / 1,022 / 1,082 ms。3回とも結果と書き込んだ値は 42。ワールド読み込みを含む時間であり、中核だけの初期化時間や完成した製品の性能ではない。

## 解釈と検証

明示的なフレームと実行キューで関数呼び出し、return、分岐を表す。起動ごとの命令数・深さ・分岐数に予算を持たせ、超過やエラーを成功扱いせず診断する。再帰的な直接呼び出しは深さと中断の制御が難しいため採らない。Java の正確な上限、順序、エラー伝播は未確認。方式 A はハンドラ内で同期実行し、保留書き込みを後で反映する。

現在の `executeCommand` は中断したジェネレーターを明示フレームとして LIFO の実行キューで進める。既定予算は命令 100,000、関数深さ 128、分岐 10,000 で、呼び出しごとにリセットする。命令は入れ子の `return run` と関数条件の内部呼び出しも数え、分岐は条件、`as`・`at` で展開した対象、呼び出す関数（タグの各要素を含む）を数える。超過時は直ちに診断して残りの処理と保留中の store を実行しないが、既に行った書き込みは戻さない。この値と超過時の伝播はランタイム独自の安全策であり、Java の上限やエラー伝播との一致は未確認。

`schedule` は予定の関数またはタグの ID と期限 tick を保持する。`scheduledFunctionCalls` は論理時刻を 1 tick 進め、同じ tick の予定から、その時点の関数定義を登録順に参照する。中核の `advanceScheduledTick` と BDS のホストがこの処理を共有する。BDS は各関数をスコア投影付きで実行してから `tick` タグを実行する（#235）。確定世代には論理時刻と順序付きの予定をスコア・storage と共に保存する。旧世代に予定の項目がない場合は時刻 0 と空の予定から開始する。BDS で予約が再起動をまたぐ検証は #200 が扱う。

Node のフェイクホストでは Java の正解データ（#96）と意味論を比較する。BDS では API 制約、起動、永続化、ネイティブとの境界を検証する。片方だけではそれぞれ API の制約または網羅と再現を確かめにくい。現在の中核は CommandIR から scoreboard・storage の一部と関数を実行する。execute の各修飾句は `runtime/execute-steps.ts` の登録表に検証と評価をまとめ、評価前に修飾句の列全体を検証する。実行コンテキストには実行者・位置・向き・アンカー・ディメンションがあり、エンティティ選択で展開したコンテキストを関数フレームに渡す。

エンティティ・ブロックを使う経路は `ExecutionHost` に候補列と操作を求める。中核では名前空間付きの Java ID（`minecraft:the_nether` など）を用い、座標を換算する。フェイクホストでは種別、タグ、距離、sort、limit を評価する経路と、セレクタを使う scoreboard players set/get を照合した。Script API との接続は後続の範囲。未知の操作は失敗を返す。

`scores=` はランタイムのスコアボードを参照する。候補の保持者名にはプレイヤー名またはプレイヤー以外のエンティティ ID を使い、指定された全 objective の値が揃って範囲に入る候補を選ぶ。`team=` と `gamemode=` は候補のチームとプレイヤーのゲームモードを参照する。いずれも並べ替えと件数制限の前に評価する。

変換器は初期化パックの `scripts/datapacks.js` に `datapacks` を出力する。`schemaVersion: 1` と保存された有効順の `packs` を持ち、各パックの `functions` は関数 ID から行順の IR codec JSON 文字列の配列への対応、`tags` は関数タグ ID から元の JSON への対応である。ワールドの版で選んだオーバーレイを順に適用する。パック順とタグの `replace`・任意参照を保持し、ワールド起動時にホストが入れ子のタグを解決する。`minecraft:load` と `minecraft:tick` も通常のタグとして保存する。版を選べないパックや、通常行の解析またはマクロ行の型紙化ができない関数は、レポートに理由を記録して関数単位で除外する。

変換器の storage 初期データは初期化パックの `scripts/storage.js` に `storage` 配列として収める。各要素は `id`（名前空間付きキー）と順序付き `chunks` を持ち、連結すると `schemaVersion: 1` の JSON になる。値は IR と同じ型付き符号化であり、`deserializeStorage` で compound に復号する。各片は UTF-8 で 32,767 バイト以下。読み取り・符号化の失敗は変換レポートの `storage.errors` に記録する。起動時に確定済み状態がなければ取り込んで確定し、以後は確定状態を復元する。管理対象 objective の fake-player スコアは BE 側の変更も取り込み、storage と共に tick 境界で同じ世代として確定する（#303）。
